# {{VAULT_NAME}} — LLM이 관리하는 지식 베이스

이 저장소는 Obsidian 볼트이자 LLM이 관리하는 위키다. 이 파일이 볼트의 **스키마**다 —
구조·페이지 형식·불변 규칙만 담고, 절차는 `llm-wiki` 플러그인의 스킬에 있다.

`CLAUDE.md`는 이 파일을 import만 한다(Claude Code와 Codex가 같은 규칙을 읽도록).
규칙을 고칠 때는 **이 파일만** 고친다.

## 역할 분담

**당신(LLM)이 위키를 쓴다. 사용자는 읽는다.** 사용자의 역할은 자료를 모으고,
방향을 잡고, 좋은 질문을 던지는 것. 당신의 역할은 요약·상호참조·분류·일관성 유지다.

## 계층

| 경로 | 소유 | 규칙 |
|---|---|---|
| `raw/` | 사용자 | **불변.** 읽기만 한다. 절대 수정·삭제하지 않는다. git 제외. |
| `wiki/` | LLM | 당신이 만들고 갱신한다. 전부 git 추적. |
| `AGENTS.md` | 공동 | 이 파일. 무엇이 잘 통하는지 알아가며 함께 고친다. |

```
raw/{{DOMAIN_DIRS}}/   원본 자료
raw/assets/                          이미지 첨부
wiki/sources/                        자료 하나당 요약
wiki/entities/                       사람·조직·장비·시스템·제품
wiki/concepts/                       기술·개념·방법론
wiki/syntheses/                      여러 자료를 종합한 결론
wiki/sessions/                       AI 코딩 에이전트 작업 기록
wiki/ideas/                          앞으로 개발·개선할 것
wiki/index.md                        내용 카탈로그
wiki/log.md                          시간순 기록 (append-only)
```

위키는 **도메인이 아니라 유형으로** 나눈다. 도메인은 프론트매터 `domain`으로만 표시한다.
그래야 개체·개념 페이지가 도메인을 가로질러 연결된다(업무에서 만난 장비가 연구 과제의
근거로 이어지는 식). 도메인별 폴더로 나누면 서로 링크가 약한 섬이 된다.

## 워크플로 — 스킬로 분리됨

| 상황 | 스킬 |
|---|---|
| 새 자료를 위키에 넣을 때 | `wiki-ingest` |
| 위키에 질문할 때 (볼트 안·밖 모두) | `wiki-query` |
| 위키 건강을 점검할 때 | `wiki-lint` |
| 다른 프로젝트의 작업을 기록할 때 | `wiki-log` |

절차는 각 스킬에 있다. 이 파일에서 중복 설명하지 않는다.

## 페이지 형식

### 프론트매터 — 모든 위키 페이지 필수

```yaml
---
type: source | entity | concept | synthesis | session | idea
domain: {{DOMAINS}}
created: 2026-01-01
updated: 2026-01-01
tags: [예시, 태그]
sources: ["[[어떤-자료-요약]]"]
status: draft | stable | contested
---
```

- `sources` — 이 페이지가 근거한 자료. **근거 추적의 핵심.** 비워두지 않는다.
- `status: contested` — 다른 페이지와 모순이 발견되어 표시된 상태.
- `updated` — 페이지를 건드릴 때마다 갱신한다.

`type: idea`는 세 필드를 더 쓴다.

```yaml
targets: ["[[대상-시스템-A]]", "[[대상-시스템-B]]"]   # 어느 시스템 건인지
stage: 제안 | 검토 | 진행 | 완료 | 보류
priority: high | medium | low
```

`targets`가 없으면 "○○ 쪽에 개선할 것 있나"에 답할 수 없다. 비워두지 않는다.
`status`(문서 신뢰도)와 `stage`(작업 진척)는 다른 축이다. 섞지 않는다.

### 유형별 뼈대

| 유형 | 구성 |
|---|---|
| `source` | 서지정보(출처·날짜·원본 경로) → 핵심 요점 → 위키 내 연결 |
| `entity` | 정의 → 속성 → **등장 이력**(어느 자료에서 언제) → 관련 개체 |
| `concept` | 정의 → **우리 맥락에서의 의미** → 관련 개념 → 근거 자료 |
| `synthesis` | 논지 → 뒷받침 근거 → **반대 근거** → 미해결 질문 |
| `session` | 무엇을·왜 → 결과 → **알아낸 것** → 후속 과제 |
| `idea` | **현재 상태**(코드·문서 근거) → 문제 → 제안 → 고려사항 |

굵게 표시한 것은 생략하지 않는다. `synthesis`의 반대 근거가 없으면 위키가
확증 편향 기계가 되고, `entity`의 등장 이력이 없으면 주장의 출처를 추적할 수 없다.
`idea`의 현재 상태가 없으면 몇 달 뒤 그 제안이 아직 유효한지 판단할 수 없다 —
파일 경로와 확인 시점을 함께 적는다.

### 파일명

한글 그대로 쓴다. 공백은 하이픈. 예: `wiki/entities/사내-모니터링-시스템.md`

## 불변 규칙

1. **`raw/`를 수정하지 않는다.** 진실 원천이다.
2. **근거 없는 문장을 쓰지 않는다.** 모든 주장은 `sources`로 추적 가능해야 한다.
3. **모순을 발견하면 숨기지 않는다.** 양쪽 페이지에 `contested`를 달고 충돌 지점을 명시한다.
4. **위키를 건드렸으면 `index.md`와 `log.md`를 갱신한다.** 예외 없다.
5. **추측을 사실처럼 쓰지 않는다.** 불확실하면 그렇게 표시한다.

## log.md 형식

접두사를 고정한다. 유닉스 도구로 파싱하기 위함이다.

```
## [2026-01-01] ingest | <자료 제목>
## [2026-01-01] session | <작업 제목>
## [2026-01-02] lint | 고아 페이지 3건 정리
## [2026-01-02] query | <질문 요지> → syntheses/<페이지>
```

```bash
grep "^## \[" wiki/log.md | tail -5      # 최근 이력
```
